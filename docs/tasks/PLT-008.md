## 一、前提（最重要的一条）——**常设授权**

**老板 2026-09-13 10:0x 补充拍板（以本条为准）**：

> **"它是修复，有时候你们因为版本或者是什么内部 bug 问题、平台 bug 问题，如果坏了，他肯定要这样修呀。"**

→ **修复类写入 = 常设能力**：**不必每救一条线都要一次点头**。
→ 上一版"逐次批准"（老板 09:5x 首肯时的写法）**作废**，按其「以老板最新一次拍板为准」更正。
→ **常设的代价 = 第④条**：**不逐次问，但每次都留痕（事后一行，含卡号 + 证据路径）**。

## 二、范围

**仅限已锁死的线**（症状 = 每轮 `Failed to deserialize … missing field call_id` / 400）。
手段 = 对**该线程自己的** rollout 账本做**就地等字节替换**（残项 → 中性留痕）＋同步投影对应那一行。
**不含**：向线程注入正文、改别的线、任何非锁死场景的写入。

## 三、四条执行口径（缺一不跑）

1. **仅限已锁死的线**（每轮 400 / 缺 `call_id`）；
2. **等字节替换**：不增删行 —— 前后**行数**与**被替换行的字节长度**实测一致；
3. 动手前**先备份**，备份路径写进留痕（账本 + 投影各一份）；
4. **每次报备**（一行，含证据路径）。

## 五、影响面 / 回滚点 / 风险

- **影响面**：**单个被修线程**（不是全仓、不是全平台）；
- **回滚点**：每次写入前的备份 —— 账本 `*.bak-callid-<stamp>`、投影 `thread_history_1.sqlite.bak-callid-<stamp>`；
- **风险**：①写坏账本 → 备份整档回滚；②误伤他线 → 只用"已 400 锁死"判据，且**事前投该线说明 + 板上留一行**（通用红线第 7 条）；③偏移错位 → 用等字节/等行数替换规避。
