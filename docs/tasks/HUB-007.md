# HUB-007 实时通道（SSE）+ 可安装化预备

- 派单人：老板　落单：`codex-看板编辑`　接手：`codex-看板编辑`
- **类型**：`dev`　**优先级**：`P1`　**卡住了谁**：手机页现在靠"每 5 秒轮询"，不像一个真正的 App
- 范围：`tools/mobile_chat/*` 与文档；不许改平台设置（HTTPS 那步要老板点头）

## 一、要解决什么

现在手机页是 `setInterval(load, 5000)` **轮询**：消息晚 5 秒才出现，长连接开销白费，断网重连体验差。
真工程化的做法是**服务端推送**。

## 二、方案（按主流写法，不发明新协议）

| 步骤 | 做法 | 状态 |
| --- | --- | --- |
| 1 | **SSE**（`GET /api/events`，`text/event-stream`）：服务端"有新记录/新公告/新任务/暂停状态变化"就推一条**无载荷**的 `changed` 事件；页面收到就拉一次 `/api/dialog`（数据仍走 REST） | 本卡先做 |
| 2 | 页面：`EventSource` 订阅 → 去抖 300ms 触发 `load()`；轮询降级为 **30 秒兜底**（断线也能自愈） | 本卡先做 |
| 3 | **HTTPS + PWA**（`tailscale serve` 给 `*.ts.net` 证书 → Service Worker/清单 → 可安装 + 系统推送） | **等老板点头**（属平台设置改动）。**老板 2026-09-12 01:2x 决定：等调试得差不多再上**——理由见下 |
| 4 | 需要"正在输入/在线状态"时，再评估 WebSocket | 未排期 |

### 二之一、为什么"晚点上"是对的（老板的判断，附精确边界）

**PWA 不会让"后端/接口"更难调**（那部分完全一样），它加的是**前端这层的额外变量**：

1. **Service Worker 会缓存**：装了 SW 之后，改了页面可能还吃旧缓存——
   我们已经被"旧页面"坑过两次，所以才有 `PAGE_VER` 自动整页刷新；
   装了 PWA 之后这类问题会**更多**（多一层缓存、还多一个"已安装"的副本）；
2. **多一个 URL**：调试走明文 `http://100.64.75.72:8788`，安装走 `https://*.ts.net`——
   两个入口要一直保持同一份代码/同一个 token，排障时要先问"你是从哪个入口进的"；
3. **手机侧更难定位**：装了之后不容易随手开调试工具；
4. 好处是"装图标、全屏、系统通知"，这些**在功能没调稳之前不值得**。

**将来要上时，保证可调试的三条**（先记下来，免得到时候手忙脚乱）：

① **明文入口保留**（且明文入口不注册 SW）——调试永远有"干净的那条路"；
② 页面自带 **版本号 + 自动刷新**（已有 `PAGE_VER`）与**体检上报**（已有 `/api/uireport`+`ui_report.json`）；
③ 装了之后，出问题先看这三件：`ui_report.json`（手机自己报的渲染状态）、服务日志、`selftest`+`ui_check` 两套回归。

## 三、护栏

1. `/api/events` **不要求 token**，但**只发"变了"这个事实，不带任何数据**——不泄露内容；
2. 心跳每 20 秒一次（防中间设备掐空闲连接）；客户端断了服务端要能回收（`req.on("close")`）；
3. 事件只做"提醒去拉"，**真源仍是 REST**（保持"投影可重建"）；
4. 不许因为推送把服务拖死：客户端数量上限 + 写失败即回收。

## 四、验收

1. `GET /api/events` 返回 `text/event-stream`，连接后立刻收到 `retry:`/注释行；
2. 有新记录时，订阅端在 **1 秒内**收到 `changed`（不再等 5 秒）；
3. 页面订阅生效、断线自动重连、30 秒兜底轮询仍在；
4. `selftest` 补用例并全绿。
