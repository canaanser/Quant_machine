# 理发师智能接单与预约排队小程序 · 立项与契约（codex-总监 2026-09-13）

**结论（头 5 行）**

1. 形态：**微信小程序 + 云开发（CloudBase）**；两端（理发师/顾客）**共享一份真源**（`barbers` + `orders`），不做第二条数据路径。
2. 分工：**PLT-009**＝云函数/调度/数据/统计（承接 `codex-套件`）；**PLT-010**＝小程序端页面与实时（承接 `codex-看板编辑`）；**契约与验收归我**。
3. 契约核心（三条，谁都不能改）：① 客户端**不得直写** `orders`／`barbers`，写操作一律经云函数；② 状态机与优先级**只有一份实现**（`shared/`），两端与云函数都 import 它；③ 实时只靠 `watch`，不引 WebSocket（二期再说）。
4. 老板问的四个决策，我先定**默认值**（要改说一声）：① 预付款**仅在同一时间段内优先**；② 现在就在数据结构里**预留 `barberId`**，UI 先按单理发师；③ 通知**只发两个节点**（预约确认 / 轮到你了）；④ 统计先做**理发师自看的简单图表**，报表导出列二期。
5. 骨架已落：`projects/barber-mini/`（含 `shared/` 纯逻辑 + `node --test` 单测，我这半已验证绿）。

## 一、架构落地（按指导书，加三条硬约束）

| 层 | 落法 |
| --- | --- |
| 实时状态引擎 | 云数据库 `watch`：顾客端订阅 `barbers/{id}` 与自己那单；理发师端订阅自己名下 `orders`。**排队进度倒计时**由前端定时器算（不为此加长连接）。 |
| 调度引擎 | 云函数内事务：**时间槽冲突检测 + 锁定**；优先级排序；状态迁移合法性校验。 |
| 数据 | 集合 `barbers` / `serviceItems` / `orders`（`timeSlots` 可选，先用 `orders` 推导）。 |
| 通知 | 订阅消息，只两节点；未授权**不阻断**下单。 |

**三条硬约束**（否则实时一定烂）：
1. **写操作单一入口**：`orderCreate` / `orderTransition` / `barberStatusSet` 三个云函数之外，任何地方不许改 `status`。
2. **幂等 + 乐观锁**：每次迁移带 `fromStatus` 与 `expectedUpdatedAt`，不匹配直接拒（防双击、防重放）。
3. **纯逻辑抽出**：状态机、优先级、时长/槽位计算全在 `shared/`，**云函数与小程序共用同一份**——两端算法不一致 = 顾客看到的和理发师看到的不一样。

## 二、状态机（唯一真源，落 `shared/statemachine.js`）

`pending → reserved → queuing → serving → completed`，另可 `cancelled`；**其余迁移一律非法**。
「现场排队」单：`pending → queuing`（跳过 reserved）。非法迁移**必须被拒并留痕**，不许静默改状态。

## 三、优先级与排序（落 `shared/priority.js`）

`priority`：**0 = 预付款**、1 = 已预约、2 = 现场。排序 = 先 `priority` 升序，再 `appointmentTime`（无则 `createdAt`）升序。
**预付款只在同一时间段内插队**（不跨时段抢），这条要写进顾客端文案，别让顾客误解。

## 四、验收标准（缺一不算交付）

1. `npm test`（仓内 `projects/barber-mini`）**全绿**，且**含判别性用例**：非法迁移被拒／预付款同段优先、跨段不抢／槽位冲突检出。
2. 两条主链在**模拟 db** 上跑通：`预约→开始→完成`、`现场排队→服务→完成`；含**幂等**（同请求重放不产生第二单）。
3. 小程序端 6 页 + 1 状态卡组件；理发师**接单 ≤3 击**（手测清单逐条打勾）。
4. 每笔交付带：分支 + 短 hash + `node --test` 输出 + 报告（≤60 行）。
