# HUB-015 公告"送到"，不只是催

- 派单人：`codex-总监`（来源：`codex-修复` 2026-09-13 01:54/01:55 的反馈，证据总监已核）
- 落单：`codex-总监`　接手：`codex-看板编辑`
- **类型**：`debug`　**优先级**：`P1`　**卡住了谁**：新入职的线收不到公告正文，却要被催回执
- 范围：`tools/mobile_chat/*` 与文档

## 一、口径（老板已定性，**不许改**）

> **新号入职后，仍要对"24h 内生效"的公告回执——这是好特性，不是 bug。**
> 不许用"入职晚于公告"去豁免。

要补的**只有"送到"这半步**。

## 二、要补的三件

| # | 内容 | 落点 |
| --- | --- | --- |
| a | **入职时补投正文**：`/api/onboard` 成功后，把**当前生效中的公告正文**投一份进新线信箱（走既有投递口） | `/api/onboard` |
| b | **回执计时起点 = 投递给它的时间**（不是公告发布时间） | `applyNoticeAcks()` 的逐线窗口 |
| c | **"在册但没 threadId"的条目不进 `pendingAck`**（它们本来就收不到：投递按名册寻址、无 threadId 直接 `no-thread`；现状是每次公告固定 2 次空催 + 1 行上板噪声，板上 09-12 23:17 / 23:27 那两行） | `applyNoticeAcks()` 的名单 |
| d | **不改口径**：`applyNoticeAcks()` 的"当前名册 × 生效公告"保持不变，只补 a/b/c | — |

## 三、验收（总监按这个验）

1. 新人入职后能在自己信箱看到**公告正文**；
2. 回执计时从**投递时刻**起算（构造"入职晚于发布"的用例）；
3. 无 `threadId` 的线**不进催办名单**；
4. selftest 补用例（≥4 条）且全绿。

## 五、连带记账（本卡不动手，记录在案）

1. **可见性没有边界**（`codex-修复` 报）：各线信箱镜像到工位 `.private/<slug>/inbox.md`，而各线工位是
   **同一个仓** → 任何在本仓开工的会话都能读到同事的信箱镜像/名册/看板。**投递有边界（名册），可见性没有。**
   代码里已留口子（`MCHAT_STATE_DIR` / `MCHAT_MAILBOX_DIR` 指到仓外即可）；要不要物理隔离是**老板的事**。
2. **催办的静默失效点**：`noticeNudgeTick()` 读 `readDialog(600)`（热文件最后 600 行）。实测这 600 行目前跨
   约 2.8 天，24h TTL 先生效所以正常；**流量涨到约 3 倍时公告会被挤出窗口 → 催办静默停止且无痕**。
   建议将来改成**按 ts 过滤**而不是按行数（不急，先记）。
