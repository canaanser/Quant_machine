# Quant Alpha System 现状说明与回测改造方案

> 文档日期：2026-08-28 ｜ 作者：小二陈 ｜ 目的：给 CTO 审阅的现状分析与改造建议

---

## 一、系统架构现状

```
┌─────────────┐     ┌──────────────────────────┐     ┌──────────────────────┐
│  stockdb    │────▶│   扫描器 scanner          │────▶│  pattern_history.db   │
│ 本地数据引擎 │     │  (录入方：建形态表)        │     │  (84只 + 20只AI龙头)   │
│ 20年A股数据  │     │  8核并行 + 暂存库 + 合并   │     │  形态/位置/冷却/收益    │
└─────────────┘     └──────────────────────────┘     └──────────┬───────────┘
                                                                 │ ❌ 没被消费！
┌────────────────────────────────────────────────────────────────▼───────────┐
│  回测引擎 core/backtest                                                │
│  现状：每天对选中股票【自己重新 scan_patterns 现扫形态】               │
│  → 不用 pattern_history 表 → 5万次重复扫描 + 缺位置/冷却信息            │
└─────────────────────────────────────────────────────────────────────────┘
```

**核心结论**：扫描器（录入）与回测（消费）**脱节**——扫描器辛苦建的表，回测弃之不用，每天自己重扫。

## 二、扫描性能（已完成优化，显著提速）

| 阶段 | 耗时 | 关键改造 |
|---|---|---|
| 最初（84只 10年） | **10 小时** | 旧代码"边识别边逐条写库"（Windows 写库瓶颈）|
| 第一次优化后 | 每只 8~14 分钟 | WAL + 批量 UPDATE + 确定性哈希 |
| 并行版 | 7只 13秒 | 识别纯内存 + 8核并行 + 主进程令牌写库 |
| **当前（暂存区版）** | **104只 2~3 分钟** | worker 独立暂存库并行写 + ATTACH 合并 + 攒批 |
| 4000只（预估） | **~1.5 小时** | 攒批合并（--merge-batch）|

**已落地的基建**：
- 并行识别（8 进程，识别与写库分离）
- 暂存库方案（worker 各写各的库，零锁竞争；主进程批量合并）
- 确定性哈希（wave_id / pattern record_id / atomic record_id，根治 UNIQUE 碰撞丢数据）
- 断点续跑（--start-at）+ 增量模式（scan_progress）
- 数据字段：位置(8档)、冷却期、120日回撤、逐日收益1~5天（无未来函数）

## 三、回测性能问题（待优化）

**回测慢的两大根源（core/backtest/pipeline.py + pattern_mixin.py）：**

1. **每天重复扫描形态（最大冗余）**
   ```
   _scan_and_fuse_patterns() 每天执行：
     for symbol in 选中股票:
         ohlc = market_data.get_ohlc(symbol)     ← 每天重载 OHLC（2500天×20只=5万次）
         scan_patterns(hist_ohlc)                ← 每天重新做形态识别（5万次重扫！）
   ```
   我们已建好的 pattern_history 表（含位置/冷却/收益）**完全没用上**。

2. **逐日全历史切片（O(N²)）**
   ```
   每天: hist_returns = returns.iloc[:i]   ← 第 i 天切前 i 天全历史
   10年2500天 → 累计312万行重复切片 + score_stocks 每天全量重算
   ```

3. **次要冗余**：每天新建 VotePool()、每天保存快照等。

**回测还缺失**：波段位置、冷却期——已被实验证明**最有价值的两个因子**（位置主导；冷却≥60天+中跌+乌云盖顶=D+5 +7.4%）。

## 四、改造方案（回测读表）

```
改造后：
┌─────────────┐     ┌──────────────────┐     ┌─────────────┐
│ 扫描器(录入) │────▶│ pattern_history  │────▶│ 回测(消费)  │
│  一次性建表   │     │  (内存索引)      │     │  每天O(1)查 │
└─────────────┘     └──────────────────┘     └─────────────┘
```

| # | 改造点 | 效果 |
|---|---|---|
| 1 | pattern 信号预加载：启动时把表按 `(symbol, date)` 建内存索引，替换每天的 scan_patterns | **5万次重扫 → 5万次 O(1) 查表** |
| 2 | OHLC 缓存一次，不再每天 get_ohlc | 省 5 万次 DataFrame 构造 |
| 3 | VotePool 实例化一次复用 | 省 2500 次重建 |
| 4 | 滚动窗口替代 `returns.iloc[:i]`（如最近120天）| O(N²) → O(N×W) |

**预期**：10 年回测 **小时级 → 分钟级（提速 100 倍+）**，且回测获得位置/冷却因子。

## 五、影响评估

| 部分 | 影响 |
|---|---|
| 扫描器 | 零影响（录入方不变）|
| 回测对外接口 | 零影响（score_series 融合逻辑不变，仅内部实现换源）|
| 策略层 | 零影响（fuse_with_patterns 等不变）|
| **回测基线** | **会变化**：信号口径从"60根窗口现扫"→"波段内预扫"，形态集合不同；新表带位置/冷却，结果应更准——需重定基线（改造后跑对照：旧现扫 vs 新查表，CTO 确认）|
| 池外股票 | 回测测 pattern_history 表外股票时查不到信号（退回无形态）；若回测需覆盖全市场 → 先扩扫描池（4000只 1.5小时）|
