## 一、要解决的问题

现在 Hub 要把消息送进某条 Codex 线，用的是 `codex exec resume <threadId>`——**直接去抢那条线程的写锁**。桌面端此刻若开着那条线，就抢不到：那一轮"没接上"，消息要么丢、要么被**兜底投给了别的线**（已发生过：老板连发三条 @某条线，全落到默认线）。

老板给的解法：**先看它忙不忙。忙就别打扰，不忙再叫。**

## 二、决策表（按员工状态）

| 目标线状态 | 判定 | 动作 |
| --- | --- | --- |
| `busy` 正在跑回合 | 在忙 | **不打扰**：只落它自己的信箱，等它这轮结束或下次开工自读 |
| `active` 且空闲 | 在岗 | 投递 + **唤醒**（门铃） |
| `offline` / `stale` 本尊不在 | 没人 | 交给**值守分线**只读代答（已有机制） |
| `retired` 已退役 | 已走 | 明确回「该线已退役」，**不投递、不兜底** |
| `unknown` 待上岗 | 空位 | 只落信箱，并在看板提示「该席位尚未上岗」 |

## 三、怎么判"忙"（三层，先粗后细，别假装能精确知道）

1. **Hub 自己的 busy 标志**（现有：`/api/ping` 返回 `busy`；duty 循环里也有并发保护）；
2. **该线最近产出时间**：近 N 秒内有过产出（看板/dialog 记录 ts）→ 视为忙；
3. **注入失败的类型**：真去试一次，若返回"占用/抢锁"类错误 → **判为忙**，退避重试（2 → 5 → 15 分钟），**不许轰炸**。

> 诚实说明：外部没有稳定途径精确知道某条桌面线程"此刻是否有回合在跑"。正确姿势是「试一次 + 把失败当忙 + 退避」，而不是假装能预知。

## 四、护栏（比功能本身重要）

1. **投不进绝不改投别人**：失败只会"留在目标信箱 + 记一条待唤醒"，**永远不再兜底给别的线**（今天那个坑的根因）。
2. **同一条线同时只允许一个在途投递**（幂等锁），避免重复唤醒、重复烧 token。
3. **退避 + 限流**：失败退避；每线每小时唤醒次数上限（与值守分线同口径）。
4. **可审计**：每次尝试（投给谁、判为什么状态、结果、退避到何时）写一行日志。
5. **常驻只在计划任务上下文**：任何 agent 不得从沙箱 shell 拉起这个提醒器。
6. **与优先级联动**：同一时刻只能送一条时取队首（规则见 `docs/priority.md`）；限流满则队首等待，**不许降级去送别人**。

## 五、验收标准（逐条可判定）

> **【must-fix · 2026-09-11 主线裁决】判忙口径必须先修**，否则本卡交付的是"永远叫不醒"。
>
> **现状证据（2026-09-11 05:4x 更正归属）**：当时查的是 `GET /api/deliver?alias=codex-量化总监`——**那是另一条线**（真实的量化总监线），不是本线；返回 `active / 本尊在忙（写锁被占）` 而该线 `lastOutputSec=14278`（≈4 小时无产出）。现象与结论不变（桌面端占窗但空闲被误判成忙），仅**归属更正**：证据取自 `codex-量化总监` 线，非 `codex-总监`。
>
> **成因**：判忙的唯一判据是"`codex exec resume` 抢锁失败"，但抢不到锁有两种成因：① 真在跑回合（该等）；② **桌面端只是开着窗口**（空闲，CLI 一样抢不到锁）。对桌面端常开的线，②会持续成立 → 永久判忙 → 永远只投信箱、永远叫不醒。看板上那一串"（本尊不在，由值守分线代答）"就是这么来的。
>
> **裁决口径（三条）**：
> 1. **忙 = 抢锁失败 且 最近产出很近**（建议阈值 90 秒：`lastOutputSec < 90`）；
> 2. 抢锁失败但最近产出很久 → 判为「**窗口占用但空闲**」，**不判忙**：有值守分线的交值守代答；没有的留在信箱，并在看板显式标注「已投递未唤醒（桌面端占用）」，**不再无限退避**；
> 3. **退避要收敛**：退避到 15 分钟仍属"窗口占用"，就停止重试，改为**等本线下次产出时补投 / 下次开局自读信箱**，不空转烧 token。
>
> **本条验收**：给一条"桌面端开着但空闲"的线投递 → 排障口 `reason` 不再是"本尊在忙"，且日志无无限退避；给一条真在跑回合的线投递 → 确实不打扰。

1. **忙时不打扰**：某条线正在跑回合时投一条 → **当次不注入、不打扰**，消息留在它信箱；
   **并且必须排定补投**（退避 2→5→15 分钟后再试），直到送达或到补投上限。
> **口径修正（老板 2026-09-11 05:0x）**：初版写的是"只落信箱、等它自读"，老板当场指出
> **那等于"永远叫得醒吗"——不，是永远叫不醒**。忙时不打扰 ≠ 放弃投递；
> 正确姿势是"先落信箱 + 记待唤醒 + 到点补投"。到达补投上限仍失败时，要在看板留一行说明
> （消息仍在它信箱、没丢、也没转给别人），**不许静默压住**。
   > **交叉判断（老板 2026-09-11 05:0x 追加裁决 · must-fix）**：**忙 = 抢锁失败 且 最近产出 < 90 秒**。
   > 抢锁失败但久无产出 = **「窗口占用但空闲」→ 不判忙**（有值守交值守；没有的留信箱并在看板标
   > 「已投递未唤醒（桌面端占用）」，**不再无限退避**）。**锁文件在 ≠ 忙**——实测有 8 小时前的陈旧锁，
   > 据此判忙会让一条四小时没产出的空闲线永远叫不醒。
2. **闲时叫得动**：该线空闲时投一条 → 能在合理时间内被唤醒并处理；
3. **绝不改投别人**：制造一次投递失败 → 记录显示"留在目标信箱 + 待唤醒"，**其它线不得收到该消息**；
4. **退避生效**：连续失败不产生密集重试（日志里能看到 2/5/15 分钟间隔）；
5. **幂等**：同一条消息重复扫描不产生重复投递；
6. **自测全绿**，且 6 条护栏各有对应用例。
