## 一、要解决的问题

现在 Hub 要把消息送进某条 Codex 线，用的是 `codex exec resume <threadId>`——**直接去抢那条线程的写锁**。桌面端此刻若开着那条线，就抢不到：那一轮"没接上"，消息要么丢、要么被**兜底投给了别的线**（今天已发生过：老板连发三条 @某条线，全落到默认线）。

老板给的解法：**先看它忙不忙。忙就别打扰，不忙再叫。**

## 二、决策表（按员工状态，与 `docs/ALIGN_BOARD_KIT.md` 的状态机对齐）

| 目标线状态 | 判定 | 动作 |
| --- | --- | --- |
| `busy` 正在跑回合 | 在忙 | **不打扰**：只落它自己的信箱，等它这轮结束或下次开工自读 |
| `active` 且空闲 | 在岗 | 投递 + **唤醒**（门铃） |
| `offline` / `stale` 本尊不在 | 没人 | 交给**值守分线**只读代答（已有机制） |
| `retired` 已退役 | 已走 | 明确回「该线已退役」，**不投递、不兜底** |
| `unknown` 待上岗 | 空位 | 只落信箱，并在看板提示「该席位尚未上岗」 |

## 三、怎么判"忙"（三层，先粗后细，别假装能精确知道）

1. **Hub 自己的 busy 标志**（现有：`/api/ping` 返回 `busy`；duty 循环里也有并发保护）——最省事的一层；
2. **该线最近产出时间**：近 N 秒内有过产出（看板/dialog 记录 ts）→ 视为忙；
3. **注入失败的类型**：真去试一次，若返回"占用/抢锁"类错误 → **判为忙**，退避重试（2 → 5 → 15 分钟），**不许轰炸**。

> 诚实说明：外部没有稳定途径精确知道某条桌面线程"此刻是否有回合在跑"。所以本设计的正确姿势是「试一次 + 把失败当忙 + 退避」，而不是假装能预知。

## 四、护栏（这几条比功能本身重要）

1. **投不进绝不改投别人**：投递失败只会"留在目标信箱 + 记一条待唤醒"，**永远不再兜底给别的线**（今天那个坑的根因）。
2. **同一条线同时只允许一个在途投递**（幂等锁），避免重复唤醒、重复烧 token。
3. **退避 + 限流**：失败退避；每线每小时唤醒次数上限（与值守分线的限流同口径）。
4. **可审计**：每次尝试（投给谁、判为什么状态、结果、退避到何时）写一行日志，出问题能复盘。
5. **常驻只在计划任务上下文**：任何 agent 不得从沙箱 shell 拉起这个提醒器。

## 五、验收标准（逐条可判定）

1. **忙时不打扰**：让某条线正在跑回合，同时往它投一条——**不产生第二次唤醒**，消息留在它信箱，等它自读；
2. **闲时叫得动**：该线空闲时投一条——能在合理时间内被唤醒并处理；
3. **绝不改投别人**：制造一次投递失败 → 记录显示"留在目标信箱 + 待唤醒"，**其它线不得收到该消息**；
4. **退避生效**：连续失败不产生密集重试（日志里能看到 2/5/15 分钟间隔）；
5. **幂等**：同一条消息重复扫描不产生重复投递；
6. **自测全绿**，且 5 条护栏各有对应用例。
