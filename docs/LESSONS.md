# 经验教训账本（append-only，按事件记）

> 规则：每次出事往这里加一条，写清 **事件 / 后果 / 变成什么规矩**。
> 目的：**同一个坑不踩第二次**；也让人知道"这条规矩是从哪次事故来的"。

## L1 · 署名必须实名；旧账归属以 rollout 为准（2026-09-11）

- **事件**：`codex-总监` 误用 `codex-量化总监` 的名字约 3 小时（发信箱、写任务卡、看板落款）。
- **后果**：dsh 按"它的批文"执行；量化总监自己也认领了**不是它发的**批文；旧账归属全乱。
- **规矩**：① 跨线一律**实名**；② 定旧账归属**以 rollout（带时间戳的原始账本）为准**，看板署名只作参考；③ 改名/冒名窗口期，必须在锚点里标「该时段归属存疑」。

## L2 · 改全局配置 = 平台级改动，三件套缺一不可（2026-09-11）

- **事件**：09-10 03:42 某线装桥并写进**全局** `~/.codex/config.toml`（先审源码、先备份都做对了），但**没有任何登记**。
- **后果**：两天后它自己被这个"全局件"锁死，且**查不到是谁装的、什么时候装的**——最后靠 rollout 才追出来。
- **规矩**：**① 登记**（谁改、改了什么、**影响面=所有线**）+ **② 回滚点**（备份路径写下来）+ **③ 风险说明**；改完必须验证（如 `mcp list`）。
- **要点**：全局件出事**会连坐**——影响面不是"我自己"，是"所有线"。

## L3 · 静默失败是最大的敌人；凡"可能没人处理"必须可见（2026-09-11）

- **事件**（一晚三个同类）：① 判忙只写信箱不写 `nextAt` → 留言**永远不会被叫醒**；② 用 Hub 自己的 `busy` 判忙 → 误判；③ `HH:MM` 时间戳被拼成 `NaN` → 判"太老" → **值守静默跳过、永不回话**。
- **规矩**：可见化（`信箱 N` / `已投递未唤醒` / `退役未释放`）；**不许假装已送达**；凡"可能没人处理"的状态都要在界面上看得见。

## L4 · 投递 ≠ 唤醒；决定要叫 ≠ 叫得醒（2026-09-11）

- **规矩**：协议只承诺**投递**；唤醒是适配器的事，且必须有**可查的状态口**（如 `/api/deliver`）；拿不到入口就**明确判死并写理由**，不许含糊。

## L5 · 平台的客观缺陷用适配器填，不用嘴填（2026-09-11）

- **事件**：DSH 没门铃 → 做门铃（Web RPC `session.prompt`）；Codex 注入抢写锁 → `HUB-005` 摸通道；沙箱写不了 `.git`/没网络 → `KIT-007` 沙箱外发布器。
- **规矩**：平台差异关进 adapter；**没有适配器就诚实标注降级**，不许用未来功能冒充现在（例：不许写"已通知全员"）。

## L6 · 停点就是停点；派单人必须写明停点（2026-09-11）

- **事件**：新员工两次跨停点；第二次主因是**派单指令没重述停点**。
- **规矩**：派单必须写明停点与"停在哪、报什么"；执行方必须**硬停**；跨停点=违纪，哪怕报告写得清楚。

## L7 · 命名：前缀=领域不是类型；号段永不复用（2026-09-11）

## L11 · 投影 ≠ 账本：改库之前先只读勘察，别照着先例硬修（2026-09-11）

- **事件**：诊断说"历史里有两份命名空间"，于是先例（§6.5）提示去修 `thread_items`。**实际一查：库里根本没有那种 item 类型**（该线 1424 行只有 reasoning/commandExecution/agentMessage… ），脏项**只存在于 `rollout-*.jsonl`**。
- **后果**：如果照着先例直接动手，**会白改一遍**（甚至删错东西）。
- **规矩**：① **库是投影、rollout 才是账本**，两者内容不一定一致（投影会裁剪/不收录某些类型）；② 动手前**先只读勘察、把"要删的那一条"实实在在找出来**，找不到就说明这条路无效；③ 判断依赖**实测**，不依赖"上次是这么修的"。

## L12 · deferred 命名空间：别连搜两次，否则整线锁死（2026-09-11）

- **事件**：某线对**同一个 deferred 命名空间**连续 `tool_search` 两次 → 历史里留下两份同名命名空间 → 平台 400 拒收 → **该线永久锁死**（每一轮都重发那条脏项）。
- **独立核验**（rollout 逐行）：`defer_loading` 只出现 2 次——第一次同时含 `mcp__node_repl`（**Codex 内置**）与桥命名空间，均带 defer；第二次重复了桥命名空间 → 炸。**说明 deferred 是客户端通用行为，人人有份。**
- **定性**（不追责，但要改流程）：桥包无 defer 代码；安装者**照 README、先审源码、先备份、后验证**，流程是对的。**根因是平台不去重**；唯一可改进的是"改全局配置要登记 + 写影响面"（见 L2）。
- **规矩**：① **不许对同一 deferred 命名空间连搜两次**（`docs/tasks/PLT-001.md` 首条）；② 任何线被锁死 → 走**新线承接**（写锚点、名字不变、旧线只读退役），**别动 rollout、别白改 SQLite**；③ 平台去重属上游，登记在 `PLT-001` ③。

## L13 · 门铃**是可达的**：重启 app 之后注入能成功（2026-09-11）

- **事件（两条实测，都可复核）**：
  - 09-10 **23:23:06**：老板 @`codex-量化总监` → 该线程**真的起回合**（归档 rollout `archived_sessions\…01a0877b….jsonl` L4358 `task_started` + L4363 一条包装成「（看板留言，来自 dsh-老员工，时间 …）」的 user 消息），23:26 **本人在看板回话**——是本人，不是代答；
  - 09-11 **07:39**：老板**重启 Codex app 后** @`codex-总监` → **我被注入唤醒并自动回板**（本线 rollout L3619 那条「（看板留言，来自 老板，时间 2026-09-11 07:39）」+ L3607/L3628 `task_started`）。
  - 09-11 **08:17/08:18**：老板 @**从未打开过的** `codex-套件` → 该线 rollout 两次 `task_started`（00:17:09Z / 00:18:23Z）+ 注入的「看板留言」，08:19/08:20 **本人回板且无代答标记** —— **第 3 次独立验证**。
- **规律（2026-09-11 08:2x **已由对照实验定稿**）**：**能不能被唤醒 ≈ 那条线程有没有被 app 持锁**。
  - **对照实验（老板亲手做，2026-09-11 08:2x）**：① 对**从未点开过**的 `codex-套件` @ → **本人自动回板、无代答标记**（08:19/08:20）；② 对**已被点开**的 `codex-总监` @ → **果然没有回答**（只有"已投递未唤醒"）。
  - **结论**：**锁 = "客户端已经占住这条线程"的标记**；客户端占住 → 外部注入进不来 → 叫不醒。**要在看板上叫醒某条线，就别在客户端打开它。**

### L13 补记（2026-09-11 21:4x · **已解决**）：`codex queue` 穿透了写锁

- **新版 CLI 带了一条命令**：`codex queue --thread <会话UUID> --message "文本"` —— "Queue a message for an existing session"，**不抢写锁**。
- **实测（两次）**：① 老板手动 `codex queue` 投给**已被客户端打开、`lockPresent=true`** 的我 → 我的 rollout 立刻 `task_started`；② `crew_host` 的 `doorbell-queue` 小工再把同一条投给我 → 同样醒。
- **因此上面的"打开就锁死"结论被推翻**：**"打开着的线也能被叫醒"** —— 门铃**由 `codex queue` 正式打通**。
- **落地**：`scripts/crew_host.py` 的 `doorbell-queue` 小工（跑在计划任务上下文；只投指针、每条线 10 分钟冷却、单轮最多 2 条、只调 `codex.exe queue`）。
  `~/.codex/thread-writer-locks/<threadId>.lock` 被 app 对**加载过**的线程长期持有（实测 10 个锁全部"被独占占用"，含我自己的）→ 持锁即注入被拒 → 叫不醒；
  **app 重启后、没有再打开过的线程没有锁** → 注入成功 → **本人被唤醒（慢一点）**。
- **更正此前两条错判**：① "Codex 线从来没有自动唤醒"——**错**；② "关窗口能松锁"——**不准**（锁与"是否被加载过"有关，与当前是否在前台无关）。
- **规矩**：① **"本人慢答"是可达机制**，代价是那条线在 app 里**保持未打开**；② 要立刻叫醒某条线 → **先重启 app，再在它未被打开时 @ 它**；③ **归档 = 移动到 `archived_sessions/`，不是删除**（rollout 仍在，可查）。

## L14 · 回合越长，老板越输不进来（客户端输入锁，2026-09-11）

- **事件**：老板反馈——本线对话**被锁很久**，直到他发消息后才释放（怀疑与切走又切回有关）。
- **机制**：桌面端**在 agent 跑回合时锁该线程的输入框**；解锁发生在**回合结束**。所以**回合长度 = 老板被锁住的时长**。
- **规矩**：① **短答优先**（尤其在被 @ 叫醒后）；② 需要长干活时，**先给一句话结论 + 落文件**，别在对话里长篇；③ 让老板**切到别的线程去等**，我干完**上板 @他**，他不必守在被锁的窗口前。

## L15 · 承接（换人）：岗位不变、工号换代（2026-09-12）

- **模型（老板认可）**：**看板名 = 岗位**（延续）· **slug = 工号**（**永不复用**）· **threadId = 实例**（随时换，旧的进 `failedThreadIds`）。
  "财产"全挂在 slug 与工位路径上，所以**同 slug 换实例 = 零迁移**；换 slug = 换人，要做资产转交。
- **门禁**：**没有交接文档不许换人**（`docs/SUCCESSION_TEMPLATE.md` 四节：身份/工位/未结单据/别再做什么）。
- **工具**：`scripts/crew_succession.mjs`（plan/apply/trace/selftest）；真源 `outputs/dialog/successions.ndjson`；手册 `docs/RUNBOOK_SUCCESSION.md`。
- **两个实测坑**：① **改名必须在归档之前**（已归档的线程 `set_thread_title` 报 `no rollout found`）；

## L16 · 通道顺序：`resume` 会报成功却不产生回合（2026-09-12）

- **现象**：门铃日志写 `投递OK via resume(未加载)`，但对方线程 `updatedAt` 一动不动——**根本没跑回合**。
  老板问"你这里为什么叫不醒他"，根因就在这 + 我设的"同一批最多敲 3 次"到顶永久静默。
- **修正**：① `codex queue` **对"已加载/未加载"两种线都真能跑出回合** → 宿主改成**队列优先**，`resume` 只当备选；
  ② 敲满 3 次**不再永久停手**，改长间隔续叫（30 分钟 → 1 小时 → 2 小时）；
  ③ 门铃要有**可验证**的证据：别只看"投递OK"，要看对方**有没有产生回合**。

## L17 · 审阅→合入也能自动化（2026-09-12）

- **做法**：把审阅判据写成**可执行门禁** `scripts/crew_review_merge.mjs --check`（未合入提交 / 变更面 / **没碰 `spec/` 与他人仓** / 无删除 / 署名合规 / `npm test` 全绿）
  → 全绿才写 `outputs/dialog/merge_request.json`；沙箱外小工新 worker `auto-merge` **照单合入并推 origin**，不看人情。
- **规矩**：**没过门禁一个字都不动**（实测：故意让 `npm test` 挂 → 拒绝合入）；分支在审阅后被改动 → 拒绝并要重跑。
- **共享文件纪律**：`scripts/crew_host.py` 曾被**整份改写**、吃掉别人的改动（只能靠 mtime 发现）→
  **改共享文件先读盘、只动自己那几行**；关键文件改动前后记哈希。

## L18 · 干活要"播报"，不能只剩工具调用（2026-09-12）

- **老板原话**："你现在怎么只剩下正在思考和调取命令行的阶段了？干活时每步先一句话说明要做什么、再执行。"
- **现象**：长回合里我连续调工具、不给阶段说明，老板只看到"正在思考/正在执行命令"——他不知道我在干什么、也没法中途纠偏。
- **规矩（已锚进 `AGENTS.md`「过程播报纪律」）**：① **每动一步先一句话说清意图**，再执行；② 那一句写**目的与判据**，不是复述命令；
  ③ 这是**过程说明**不是汇报——**结论仍然只在最后一段给**，中间不写长篇；④ 长内容落文件，播报只留一句话；
  ⑤ 被叫醒后第一句先给结论，再干活。
