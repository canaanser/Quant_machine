## 一、问题（已复现，2026-09-11 05:21）

给 `codex-套件` 投一条：**投递成功**（`dialog.ndjson` + 它的信箱 `pending_codex-kit.ndjson` 都落定），
但**唤醒失败**——线程仍 `idle`、工位里没有新产物（准备单没出现）。看板按新口径诚实播报：
「**已投递未唤醒**：桌面端占着这条线的窗口、但没在跑回合（抢锁失败）」。

**判定层已经是对的**（能区分"真在跑回合"和"窗口占着但空闲"，也不再无限退避）。
卡住的是**最后一段物理通道**：

> Hub 往某条线注入，用的是 `codex exec resume <threadId>`——它**要拿那条线程的写锁**。
> 桌面端常开的线**写锁常驻**，于是抢锁型注入在通道层面**注定失败**，不是判定层能修的。

结论：**"决定要叫" ≠ "叫得醒"**。全自动现在只差这一环。

## 五、实测结论（2026-09-11 06:4x，`codex-总监` 亲测，**全程只读、未起 daemon**）

### 5.1 协议已全量导出（**门铃的说明书**）

命令：`codex app-server generate-json-schema --out <目录>`（产物约 1.5 MB，含 v1/v2；本次落在 `outputs/app_server_schema/`，**可再生，不必入库**）。

| 类别 | 方法 |
| --- | --- |
| **门铃原语** | **`turn/start`**（在既有线程里起一个回合）、`thread/resume`、`thread/injectItems`、`turn/steer`、`turn/interrupt` |
| 只读查询 | `thread/list`、`thread/read`、`thread/itemsList`、`thread/turnsList` |
| **判忙的真信号** | `turnStarted` / `turnCompleted` / `threadStatusChanged` 事件流 → **判忙可精确**，不必再靠"抢锁失败"猜 |

> `turn/steer` 与 `turn/interrupt` 的存在意味着**"打断正在跑的回合"在协议层是支持的**——比我们此前判断乐观，值得优先验。

### 5.2 三条连接路径实测（**全部不通**）

| 路径 | 结果 |
| --- | --- |
| `codex app-server proxy`（默认控制套接字 `~/.codex/app-server-control/app-server-control.sock`） | `os error 10050`（套接字不存在/已死） |
| `codex app-server proxy --sock \\.\pipe\codex-ipc` | **沙箱内 `10013`（访问被拒）**；**沙箱外 `10061`（无人接受）** |
| `codex app-server daemon version` | **"lifecycle is only supported on Unix platforms"** → Windows 上 CLI 不管理 daemon |

### 5.3 结论

1. **通道存在、协议清楚**，但**Windows 上当前没有可用的控制端点**；
2. **沙箱内连 IPC 会被拒（10013）** → 任何门铃实现**必须跑在沙箱外**（计划任务上下文），与 `net_guard` / 看板服务同层；
3. 剩余候选（按可行性）：
   - **(a) `codex remote-control start`**：起一个带 remote control 的 app-server。**⚠️ 起常驻 = 红线，必须老板点头 + 计划任务上下文**；且**必须先验它能否接管桌面 app 里既有的线程**（不同实例可能管不到）；
   - **(b) GUI 自动化**：在桌面 app 里模拟输入并发送——丑但可行，需 app 在前台；
   - **(c) 等平台**：Windows 支持 daemon lifecycle，或 app 对外暴露控制端口。
4. **判死判据更新**（三条约束：只读 / 不改平台 / 不抢锁）：
   - 控制套接字 ❌（10050）、命名管道 ❌（10013 / 10061）—— **已判死**；
   - 第三种（沙箱外守护 + `remote-control`）**未试**（因涉红线），**未判死**。

### 5.4 当下的现实机制

在 3(a) 被老板批准之前，**"拉模式 + 值守代答"是唯一现实机制**，而且**它已经跑通**：
① 手机状态栏「信箱 N」让"压着没人处理"可见；② 开工自检第一步就是读自己信箱；③ 值守分线只读代答。

**禁止**：在没有老板点头的情况下尝试起 daemon；**也不要再重复摸** 5.2 里已判死的那两条路。

### 5.5 【重要更新 2026-09-11 07:4x】注入**是能成功的**——条件是"app 刚重启、且该线程未被加载"

| 时间 | 事件 | 可复核证据 |
| --- | --- | --- |
| 09-10 **23:23:06** | 老板 @`codex-量化总监` → 该线程起回合，23:26 本人回板 | 归档 rollout L4358 `task_started` + L4363「（看板留言，来自 dsh-老员工…）」 |
| 09-11 **07:39** | 老板**重启 app 后** @`codex-总监` → 被注入唤醒、自动回板 | 本线 rollout L3619「（看板留言，来自 老板，时间 2026-09-11 07:39）」+ L3607/L3628 `task_started` |

**规律（当前最佳解释）**：能不能唤醒 ≈ **那条线程有没有被 app 持锁**。锁由 app 对**加载过**的线程长期持有（实测 10 个锁全被独占占用）；**重启后未被再打开的线程没有锁** → 注入成功 → **本人被唤醒**。

**因此本卡结论修正**：

- ❌ **不是"通道判死"**——注入通道**可用**，只是被 app 的写锁挡住；此前判死是因为"当时相关线程全被加载过"；
- ✅ **正解（零成本）**：**先重启 app、且不要打开目标线的窗口，再 @ 它**；它不是被"推醒"，而是被注入后**自己起回合**；
- ⚠️ **仍待复验**：重启后 @`codex-套件` / `codex-量化总监`（都不打开窗口），看是否同样自动起回合；通过即写为正式机制；
- 三条约束（只读 / 不改平台 / 不抢锁）**仍然成立**——本发现没绕开任何一条，只是换了"在锁松开时投递"的时机。

### 5.6 【决定 2026-09-11 08:3x】GUI 自动化门铃：**不做**

- 老板原话：**"按这条路又费资源，又不稳定，我直接放弃。"**
- **不做的理由**：① 要常驻 + 每次抢焦点/驱动 UI，**费资源**；② 依赖窗口/控件/输入法/分辨率，**天生不稳**，收益不抵维护成本。
- **因此 Codex 侧门铃的最终形态定格**：
  1. **条件性唤醒**：**不打开就能叫醒**（未加载的线程没有写锁 → 注入成功 → 本人起回合）；
  2. **打开即上锁**：被点开过的线程只能走**代答**（新口径：引述/未决，纯礼貌话不回）；
  3. **投递有兜底**：`crew_host` 每 5 分钟把信箱镜像到工位 `inbox.md`（拉模式）；
  4. **必达/准时的活交给 DSH 线**（它的门铃是平台级的、稳定）。
- **以后不要再重提 GUI 方案**，除非平台侧出现官方接口。

### 5.7 【已解决 · 2026-09-11 21:4x】门铃打通：`codex queue` 穿透写锁

- **新命令**：`codex queue --thread <会话UUID> --message "文本"`（"Queue a message for an existing session"）——**不抢写锁**；
- **实测**：对**已被客户端打开、`lockPresent=true`** 的线投递 → 该线立刻 `task_started`（两次独立验证：老板手动一次、`crew_host` 小工一次）；
- **落地**：`scripts/crew_host.py` 新增 `doorbell-queue` 小工（计划任务上下文运行；**只投指针**、每条线 10 分钟冷却、单轮最多 2 条、只调 `codex.exe queue`）；
- **判死结论作废**：5.2 的"注入通道判死"、5.6 的"GUI 方案"都不再需要——**门铃用平台自带命令解决**。
