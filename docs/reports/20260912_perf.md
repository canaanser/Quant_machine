# 性能上限：先量后改（2026-09-12 01:1x）

老板："**想办法提高我们的性能上限，用任何方法都可以。需不需要我下一个 Flutter？**"

## 一、先量：瓶颈在哪（不是前端）

| 对象 | 体量 |
| --- | --- |
| `board.mjs` | 235KB / 4755 行（页面+服务挤一个文件） |
| `dialog.ndjson` | 395KB / 511 条 |
| `COMMS_BOARD.md` | 242KB / 445 行 |

`/api/dialog` **20 次串行基准（改前，线上 .47）**：

```
mean=220.2ms  p50=216.0ms  p95=244.3ms  max=275.0ms
```

**根因**：一次请求里同一个文件被**反复整读+重解析**——

1. `readDialog()` 每次都 `readFileSync` 整个 dialog 再 `JSON.parse` 全部行，而它在一次请求里被调用 **5～15 次**
   （每条记录判定、代答检索、投递判定各来一遍）；
2. `catchUpDialog()` **一次请求跑两遍**，每遍都把 240KB 看板整读 + 逐行正则，还扫 inbox / bridge；
3. `readAgents()` 一次请求读 ~10 次；`mailboxPendingFor()` 每条线读一次信箱文件。

## 二、改了什么（都只是"一次解析、多处复用"，语义不变）

| # | 改动 | 手法 |
| --- | --- | --- |
| 1 | `readDialog()` 解析缓存 | 按 `(mtime,size)` 缓存整份解析结果；文件没变直接复用数组 |
| 2 | `catchUpDialog()` 四个入库器各自加缓存 | 看板 / 进度流 / inbox / 桥：文件或目录没变就跳过重扫（一次请求的第二遍=免费） |
| 3 | `readAgents()` 缓存 | 写名册（注册/绑定）处**主动失效**缓存，避免同毫秒读到旧值 |
| 4 | 信箱计数缓存 | `readMailboxLines()` 按文件 `(mtime,size)` 复用解析结果 |
| 5 | **历史归档轮转**（长期上限） | 热文件超 4MB → 把老行挪去 `dialog.ndjson.archived`，热文件只留最近 2000 条；**id 一个不丢**（归档也装进 `dialogIds`，读端把"归档+热"拼起来 → **对读端透明**） |

## 三、改后（同一台机、同一数据、同一脚本）

```
改前：  mean=220.2ms  p50=216.0ms  p95=244.3ms  max=275.0ms
改后：  mean= 35.3ms  p50= 28.2ms  p95= 42.6ms  max=144.5ms      → 约 6.2×
8 并发：总 196ms（平均每条 25ms）
/api/tasks（66 条）：27ms
```

**前端一行没改**——证明瓶颈在服务端 I/O，不在渲染。

## 四、关于 Flutter：**先不下**

理由（按分量排序）：

1. **瓶颈已定位在服务端**，已经用数据证实并把 220ms 打到 35ms；换技术栈解决不了这类问题；
2. 手机端现在已经是 **SSE 秒级推送 + 联系人 + 群组 + 任务表**，Flutter 重写＝**把已有功能全部重做**，
   而**接口完全一样**（REST + SSE），收益主要是动画顺滑度；
3. Flutter 真正独有的好处只有两样：**后台推送**与**深度原生能力**。这两样在 Web 上也能拿到，
   前提是 **HTTPS**——`tailscale serve` 一条命令就能给 `*.ts.net` 上证书（比换栈便宜一个数量级）；
4. **将来真要 App，建议顺序**：① HTTPS + PWA（可装图标/全屏/离线壳/系统通知）→
   ② 若还缺"后台常驻/深度原生"，再做**薄壳客户端**（Flutter 只做壳与通知，页面复用现有 Web 层），
   **不要重写**。
