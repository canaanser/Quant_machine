# PLT-002 沙箱外小工宿主（crew-host）

- 派单人：老板（口述："我可以用管理员权限起个进程，一直帮忙开机启动"）　落单：`codex-总监`
- **类型**：`dev`　**优先级**：`P1`　**卡住了谁**：门铃 / 投递镜像 / git 发布器（`KIT-007`）三件都缺一个"沙箱外的落脚点"
- 范围：`scripts/`、计划任务注册脚本；**只做搬运，不做决策**

## 一、为什么需要它（实测结论）

**门铃（把消息投进既有 Codex 线程）在 Windows 上走"标准通道"已判死**（`codex-总监` 07:0x 亲测，全程只读）：

| 路径 | 结果 |
| --- | --- |
| 控制 UDS `~/.codex/app-server-control/app-server-control.sock` | `10050`（不存在/已死） |
| `codex app-server proxy --sock \\.\pipe\codex-ipc` | **官方客户端也拒连（10061）** |
| 裸连 `\\.\pipe\codex-ipc` | **能连上、一开口就被关**（私有握手，不认 JSON-RPC） |
| `codex app-server daemon version` | **"lifecycle is only supported on Unix platforms"** |
| `codex app-server generate-json-schema / generate-ts` | ✅ 都能导出（协议公开，**只是 Windows 上没有对外开口**） |

**另有一条硬事实**：**从 agent 沙箱连 IPC 必被拒（10013）** → 一切"要碰宿主/平台"的活，都必须跑在**沙箱外**。

## 二、设计：一个进程，清单化的小工

**形态**：**一个**计划任务（登录自启、管理员上下文），跑一个小调度器；**不是每件事起一个进程**。

**清单（每个小工都要能单独关、能 dry-run、只做搬运）**：

| 小工 | 干什么 | 现状 |
| --- | --- | --- |
| `mirror-mailbox` | 把各线信箱里压着的留言**镜像**一份到它们的工位（解决"它读不到信箱"） | 待做 |
| `git-publisher` | 替沙箱内的线提交/推送（`KIT-007`） | 待做 |
| `doorbell` | 唤醒（**标准通道已判死**；只剩 GUI 自动化 / 等平台） | 见 §四 |
| `heartbeat` | 写心跳文件，让"小工还活着"可见 | 待做 |

**纪律（红线）**：

1. **只做搬运，不做决策**——不许代替任何线"同意/批准/派单"；
2. **不碰引擎 / 托盘 / stockdb**（9/10 事故根因）；
3. 每个小工**独立开关 + dry-run**；出错退避、绝不轰炸；
4. 一切动作写日志（谁触发、做了什么、结果），可审计；
5. 注册/变更按**红线三件套**：登记（影响面=所有线）+ 回滚点 + 风险说明。

## 三、先做哪一个小工

**`mirror-mailbox` 优先**——它**不依赖任何私有协议**，纯文件搬运，收益立刻可见：
把 `outputs/dialog/pending_<slug>.ndjson` 里"比该线上次发言更新"的条目，抄一份到 `D:\<工位>\.private\<slug>\inbox.md`；
这样"线读不到自己信箱"这个缺口就填上了（`codex-套件` 现在就是这个处境）。

## 四、门铃：剩下两条路

1. **GUI 自动化**（宿主可做）：把消息打进 app 输入框并回车。
   **⚠️ 必须先做安全设计**，否则风险高于收益：① **白名单窗口**（只认 Codex 主窗口的进程/窗口类，绝不许落到交易终端或其它窗口）；② 发送前二次校验；③ dry-run；④ 一键停；⑤ 全程录屏/日志。
2. **等平台**：Windows 支持 daemon lifecycle，或 app 对外暴露控制端口（届时 `turn/start` 直接可用）。

## 五、验收标准

1. 宿主**一个**计划任务、登录自启、可一键停；
2. `mirror-mailbox` 跑通：某条线压着的留言**出现在它工位的 `inbox.md`**，且重复跑幂等；
3. 有三个开关：**总开关 / 单个小工开关 / dry-run**；
4. 日志可审计；**不碰引擎/托盘/stockdb**（有验证）；
5. 一页报告 + 登记（影响面/回滚点/风险）。

## 六、备注

- 宿主在套件里的对应物：`adapters/*` + `install/`（沙箱外运行的那一层）——**它本身就是套件要打包的东西之一**。
- 门铃若最终只能靠 GUI 自动化，**那它就是"适配器填平平台缺陷"的最典型例子**，不是权宜之计。

## 七、变更记录

### 2026-09-11 09:0x · 消除每 5 分钟一次的 cmd 闪窗（**平台级改动，按纪律登记**）

老板反馈："**动不动就来个弹窗，然后瞬间又消失，就那个 cmd**"。

**只读排查**（列全部按间隔重复的计划任务 + 读 PE 子系统判 GUI/控制台）：

- 我们的任务里只有一个"控制台子系统 + 周期触发"的组合：**`QuantCrewHost` 用 `python.exe` 每 5 分钟跑一次**
  → 每次都在桌面闪一个黑框。其余（`QuantNetGuard`/`QuantWatchDog`/`DSH-Board-Sentinel`）分别是
  GUI 的 `量化看守.exe` 与 `pythonw.exe`，不闪。

**改了什么**

| 项 | 值 |
| --- | --- |
| 目标 | 计划任务 `QuantCrewHost` |
| 变化 | `Execute: E:\python\python.exe` → **`E:\python\pythonw.exe`**（其余参数不变） |
| 影响面 | **仅这一条任务**；宿主逻辑与频率（5 分钟/`--once`）不变；因为它自己写日志文件，换 `pythonw` 不丢诊断 |
| 同步改 | `tools/register_crew_host.ps1` 的默认 `-Python` 改成 `pythonw.exe`（防止重新注册时又变回会闪窗的 python.exe） |

**回滚点（一条命令还原）**

```powershell
$a = New-ScheduledTaskAction -Execute 'E:\python\python.exe' -Argument '-B "E:\stockgate\Quant_Alpha_System\scripts\crew_host.py" --once' -WorkingDirectory 'E:\stockgate\Quant_Alpha_System'
Set-ScheduledTask -TaskName QuantCrewHost -Action $a
```

**风险说明**：`pythonw` 没有控制台 → 未捕获异常不会有屏幕输出。缓解：宿主自带日志/心跳文件；
验证时确认心跳文件**仍在增长**。

**验证（已做）**

- `Execute` 已变为 `pythonw.exe`；
- `Start-ScheduledTask QuantCrewHost` 后 `outputs/crew_host_heartbeat.txt` 由 58 字节 → 59 字节（**仍在正常干活**）。
