## 一、结论

1. **门铃打通（端到端已验证）**。`POST /api/<namespace>/<method>` + 签名 cookie，可向会话投递 prompt，不需要 GUI、不需要老板在场。实测链路：`session/list`（列出 24 个真实会话）→ `session/create`（新建隔离测试会话）→ `session/prompt`（测试会话 1 秒内回「门铃-OK」）。
2. **5 分钟保温链成立（已验证；但按当前形态不建议默认开）**。6 轮心跳 18:24:42→18:49:42 **全部准点、零漏投、漂移 ≤ 90ms**。成本的关键是**每次唤醒都要重喂一整份上下文（输入）**，保温只是让这份输入走缓存价；**输出只有每轮 5–19 token**。所以链的成本按目标会话上下文算：10k 小会话 ≈0.63 M/交易时段，**老板主会话（219k）≈14.5 M**（详见 §3.3）。可是门铃本身能唤醒**冷**会话——**已实测**：对一个最后活动在 04:39、早于 17:23 重启、其 agent 在当前进程内不可能存活的空白会话投 prompt，0.9 s 内就回了一轮。所以时间驱动不必用保温链实现——**由计划任务在守盘时刻直接点名，比每 5 分钟空转便宜约一个数量级，且每次点名都带信息**。
3. **修正移交文档的一处误记**：真实 RPC 端点不是 `POST /api/remote.mux`（那是 Typert Remote 的 **WebSocket 流**路由，带有效 cookie POST 它返回 **404**），而是 **`POST /api/session/<method>`**。此前"`?token=` 换完仍 401"的根因是**用了重启前轮换掉的旧 token**。

## 二、门铃协议（可照此复现）

| 步骤 | 请求 | 要点 |
|---|---|---|
| ① 取 token | 读 `/home/lgy/.dsh-web.log` 的 `token=` 行 | **每次 `dsh web` 重启轮换**；log 由启动重定向写入即可程序化读取 |
| ② 换 cookie | `GET http://127.0.0.1:3080/?token=<token>`（Host 必须 `127.0.0.1:3080`，GET + 路径 `/` + 唯一 token 参数） | 回 **303 + `Set-Cookie: dsh-auth-<b64url(sha256(Host))>=v1.<payload>.<sig>`**；**cookie 与 Host 绑定**，换 host/port 即换名 |
| ③ 调用 | `POST /api/session/<method>`，头 `content-type: application/json` + `Cookie:` | 信封见下；cookie 跨重启仍有效（签名密钥持久，证据强度见 §五） |

信封：

```json
{"type":"client-request","rpcId":"<uuid>","method":"session/<method>","payload":{"args":{"<参数名>":<值>}}}
```

- `method` 必须与 URL 端点串**逐字相同**，否则 `gateway/bad-request`。
- `args` 是「参数名→值」映射，参数名取自服务端方法签名：`session/list` → `{"_request":{}}`；`session/prompt` → `{"request":{…}}`。多写或漏写字段都会 `gateway/arguments-invalid`（错误里直接点名缺哪个字段）。
- `session/prompt` 必填：`sessionId` / `requestId` / `mode`（`"queue"` 或 `"steer"`）/ `content: [{"type":"text","text":"…"}]`。
- 鉴权顺序：Host/Origin 信任栅栏不过 → **403**；cookie 缺失或失效 → **401**。

## 三、实测数据

### 3.1 门铃

| 探测 | 结果 |
|---|---|
| `GET /?token=<launchToken>` | `303` + `set-cookie`（cookie 名如常取到，未记录值） |
| `POST /api/session/list` | `ok=true`，24 个真实会话（含标题/轮数/token 用量投影） |
| `POST /api/session/create` | 新建 `session-efe0cdb0-…`（cwd `/tmp/ar001-warm`，与老板会话隔离） |
| `POST /api/session/prompt` | `accepted=true`；该会话 1.2s 内产出回复「门铃-OK」 |
| `POST /api/remote.mux`（带有效 cookie） | **404 not found** —— 证明它不是 HTTP RPC 端点 |
| 同一 `requestId` **同毫秒连投 2 次** | **开出 2 个回合**（竞态窗口） |
| 同一 `requestId` **间隔 6s 连投 2 次** | **只开 1 个回合**（去重生效） |
| 对**确定已冷**的会话投 prompt | `accepted=true`，0.9 s 产出 1 轮回复「冷唤醒-OK」（见 §六） |

> 触发器含义：`requestId` 去重**不是同秒幂等**。重试必须拉开间隔（建议 ≥5s），并把"这一轮是否已经开过"写进触发器自己的状态里，不能只靠 requestId 兜底。

### 3.3 成本（实测 token，不含价格常数）

**先立一条本次实测直接验证的定律**：一次唤醒的**输入** token ≈ **该会话的上下文规模**（`pressureTokens`），**保温不保温都一样**——热会话只是让这份输入走缓存价，冷会话走未命中价。**输出极小**：每轮 5–19 token（「心跳-OK」级别）。

证据（两组，误差 <1%）：

| 观测 | 上下文 `pressureTokens` | 一次唤醒的输入用量 |
|---|---|---|
| 空白会话**冷投**一次 | 8 712 | 392 未命中 + 8 320 缓存读 = **8 712** |
| 测试小会话保温心跳（每轮） | 10 049 | ≈ 9.5 k |

所以成本必须按**目标会话的上下文规模**算，不能拿小会话的代表值外推：

| 目标会话上下文 | 单轮输入 ≈ | 5 分钟链 66 轮/交易时段 | 改成定时点名 8 次/天 |
|---|---|---|---|
| 10 k（本次测试小会话） | 9.5 k | ≈ 0.63 M | ≈ 0.08 M |
| 23 k（守盘设置会话） | 23 k | ≈ 1.5 M | ≈ 0.19 M |
| **219 k（老板主会话）** | **219 k** | **≈ 14.5 M** | ≈ 1.75 M |

（上表全是**输入** token；输出按每轮 ≤20 计，66 轮也只有 ≈1.3 k，可忽略。）

折算成钱需老板提供单价常数：`费用 ≈ 未命中输入×p_in + 缓存读×p_cache + 输出×p_out`。两处必须注意：

- 本报告早先版本的「0.63 M/交易时段」是拿 **10k 小会话**算的，套到主会话要 **×22 ≈ 14.5 M**——**不要用小会话的数字估主会话**。
- 缓存命中率**不保证**：冷唤醒或缓存过期时，这 219 k 会按**未命中价**计入，单价更高。

## 四、建议

1. **时间驱动走「计划任务定时器 → 门铃点名」，不要用 5 分钟保温链。** 守盘时刻表一天 6–8 次（09:20 / 10:30 / 13:05 / 14:35 / 15:05 / 20:45），比 66–90 次空转心跳省约一个数量级，且每次都是有效信息。冷会话会被 `session.prompt` 直接恢复（§三.1 末行、§六 已实测），不需要"保温"。
2. **保温链降为兜底**：只有在门铃凭据不可用（token 轮换丢失 / `dsh web` 进程挂了）而必须靠平台原生能力时，才启用 `schedule` overlay 顶上——它不需要凭据。
3. 触发器沿用决策书三条硬约束：挂**计划任务上下文**、**禁止在任何 agent 沙箱里拉起**（9/10 `WinError 10013` 的教训）、**只注入提示，不碰下单与资金**。
4. **唤醒词要极简（「在吗？」级别），并明确要求对方只回一行。** 这不是为了省当轮 token（5–20 个 token 的差别可忽略，钱花在重喂整段历史上），而是因为**每次唤醒都永久写进目标会话的上下文**：实测每轮追加 ≈160 token，一天 66 轮 ≈ +10 k，而这 +10 k 之后**每一轮都要重新付钱**。优先级：**少唤醒 ＞ 敲小会话 ＞ 写短话**。实践折中：用 2–4 个字的事件标签（`心跳断` / `同步完` / `尾盘自检`）代替纯「在吗？」，多几个 token 换掉一整轮澄清。
5. **缓存不必靠"网页常开"来保**：实测一次冷唤醒（距上次活动 14 h）的 8 712 个输入里仍有 **8 320 命中缓存**。网页常开只是让缓存更稳，不能改变"每次唤醒重喂一整份上下文"这个事实。

### 4.x 与 DSH 提议的三方案（A 看板哨兵插件 / B 外部哨兵 + RPC / C schedule 重复提醒）的对照

**先纠正三条，再谈取舍。**

1. **A 的「0 token」只覆盖哨兵，不覆盖唤醒。** 插件扫看板确实是 0 token（进程不是模型），但一旦 followup 到长会话，那 219 k 上下文一分不少。A 与 B 在**唤醒成本上完全等价**，差别只在哨兵住在哪、要不要凭据。
2. **「只有 C 能长期保持唤醒」不成立。** B 的哨兵挂在计划任务里就是 24 h 常驻，同样是"哨兵一直盯着、只在事件发生时才花钱"。C 的独特点只有"平台内建、零外部依赖"。
3. **「卡点：需要老板私发 `?token=` URL」已经过期。** 本次攻坚直接从 `/home/lgy/.dsh-web.log` 读到了 token，B 的通路**今晚已端到端打通**，老板不需要私下交任何东西。

**取舍（我不同意把 A 当主路）：**

| 维度 | A 看板哨兵插件（进程内） | B 外部哨兵 + RPC |
|---|---|---|
| 凭据 | 不需要 ✅ | 需要 token→cookie（已打通） |
| 平台改动 | **要改 profile + 重启 `dsh web`**（打断在用会话）❌ | 不碰平台配置 ✅ |
| 故障域 | 哨兵住在 dsh 进程里，插件异常可能拖累 GUI；**被监控者监控自己**，静默失效没人报 ❌ | 独立进程，挂了能自报，符合"自动链失效→退回投 inbox + 看板 @老板" ✅ |
| 能否唤醒冷会话 | 按其描述的 `agent.followup` 机制**依赖会话活着**（同 schedule 的限制）❌ | **实测可唤醒冷会话**（凌晨 3 点的事件也接得住）✅ |
| 升级兼容 | 平台升级可能打断插件 ❌ | 平台升级不影响哨兵主体 ✅ |

**结论**：A 的可取之处是"**不依赖凭据**"这条退路（token 拿不到 / RPC 协议变更时顶上），不应作为主路；主路用 B（凭据已就位，只差把哨兵挂进计划任务）。三条旋钮里"**看板短问答改走 `dsh --profile headless` 一次性空会话**"应立刻采纳——实测空会话上下文 8.7 k vs 主会话 219 k，差 25 倍。

**成本对照（target = DSH 长会话 219 k）**：

| 做法 | 每次唤醒输入 | 一天的输入量级 |
|---|---|---|
| C：5 分钟链跑满 24 h（288 轮） | 219 k | ≈ 63 M ❌ |
| C：只在交易时段（66 轮） | 219 k | ≈ 14.5 M ❌ |
| A/B：事件驱动（决策书节流 ≤20 次/天，实际 5–10 次） | 219 k | ≈ 1–2 M（上限 4.4 M） |
| 看板短问答走 headless 空会话 | 8.7 k | 20 次 ≈ 0.17 M ✅ |

## 五、风险与未验证项

- **cookie 跨重启**：代码 + 文件证据（签名密钥持久在 `~/.dsh/.credentials.yaml` 的 `client-connection/browser-session` 记录，该文件 mtime 早于 17:23 那次重启；校验只比对 authority 与签发/过期时间）。**未做真实重启复测**——重启会打断老板正在用的会话，需老板点头才做。
- **依赖 `dsh web` 存活**：进程没了门铃即失效（3080 无监听）。触发器必须有"健康检查不过 → 退回投 `outputs/inbox/` + 看板 `@老板`"的兜底。
- **token 轮换**：每次重启轮换，触发器收到 401 时必须自动重读日志换 cookie（本次已实现并验证该重试路径）。
- **权限面（读 + 写，务必按密码级保管）**：cookie = 该实例的**会话控制权 + 会话读取权**。一次 `session/list` 会返回**全部会话的标题、上下文规模、token 用量，以及最近几轮的问答摘要**——实测中老板给会话起的名字、他本人的对话片段都在同一个响应里。因此：只落仓库外 0600 级文件，绝不入 git / 看板 / inbox；调用方自律——**哨兵只调 `session/prompt`，不调 `session/list`**。
- **冷投递**：**已实测通过**（§六）。这意味着"靠保温链维持热窗口"不是必需的——但**代价会转移到每次唤醒的上下文规模上**：对现有 219k token 量级的主会话投一次，就是一次 219k 输入（保温与否都一样，见 §3.3）；可用的降价手段只有"让唤醒目标保持小上下文"或"依赖 provider 缓存未过期"。
